# AGENTS.md — massage-booking-bot

## Цель проекта

Создать Telegram-бота для массажиста, через которого клиент может:

- посмотреть доступные даты и время;
- записаться на свободный слот;
- посмотреть свои записи;
- отменить запись;
- перенести запись;
- получить автоматическое напоминание.

Массажист должен через Telegram видеть свой график, свободные и занятые слоты, управлять расписанием и получать уведомления о новых, изменённых и отменённых записях.

Google Calendar используется как основной календарь мастера и синхронизируется с ботом.

---

## Основной стек

Использовать:

- Node.js
- TypeScript
- Telegraf
- PostgreSQL
- Prisma ORM
- Google Calendar API
- node-cron для напоминаний (планировщик поверх таблицы `Reminder`, см. раздел «Напоминания»)
- Zod для валидации
- dotenv для конфигурации
- Luxon для работы с датами и часовыми поясами
- Vitest для тестов

Нативный `Date` не использовать для арифметики с рабочими часами: `Europe/Kyiv` переходит на летнее время, и ручные вычисления ломаются дважды в год.

Для MVP не добавлять отдельный frontend.

Интерфейс клиента и массажиста — Telegram.

## Основной пользовательский сценарий

### Запись клиента

1. Пользователь нажимает `/start`.
2. Бот показывает главное меню.
3. Пользователь нажимает `Записаться`.
4. Бот показывает доступные даты.
5. Пользователь выбирает дату.
6. Бот показывает только свободные слоты.
7. Пользователь выбирает время.
8. Бот запрашивает:
   - имя;
   - телефон;
   - при необходимости тип массажа.
9. Бот показывает подтверждение.
10. После подтверждения:
    - слот повторно проверяется;
    - создаётся запись в БД;
    - создаётся событие в Google Calendar;
    - клиент получает подтверждение;
    - массажист получает уведомление.

Нельзя создавать запись без повторной проверки доступности слота непосредственно перед сохранением.

## Слоты

Настройки:

- продолжительность сеанса;
- технический перерыв после сеанса;
- шаг отображения доступных слотов.

Пример:

```text
sessionDuration = 60 min
bufferAfter = 15 min
```

Если запись начинается в 12:00, следующий слот не может пересекаться с интервалом:

```text
12:00–13:15
```

### Решение: `endAt` и `blockedUntil`

У записи два конца, и путать их нельзя:

```text
startAt      = 12:00   начало сеанса
endAt        = 13:00   конец сеанса        (startAt + service.durationMinutes)
blockedUntil = 13:15   конец занятости     (endAt + service.bufferMinutes)
```

Правила:

- `endAt` — это то, что видит клиент и что уходит в Google Calendar как длительность события;
- `blockedUntil` — это то, по чему считается занятость и работает ограничение непересечения;
- буфер клиенту не показывается и в текст события не попадает;
- оба поля хранятся в БД, `blockedUntil` не вычисляется на лету, потому что `bufferMinutes` услуги может измениться позже, а уже созданная запись должна сохранить свои границы.

## Google Calendar

Google Calendar является внешним источником занятости.

При расчёте доступных слотов учитывать:

1. записи из БД;
2. события Google Calendar;
3. вручную заблокированное время;
4. рабочие часы;
5. исключения.

При создании записи:

1. проверить доступность;
2. создать запись в БД;
3. создать Google Calendar event;
4. сохранить `googleEventId`.

При отмене:

- отменить запись в БД;
- удалить или пометить отменённым событие Google Calendar.

При переносе:

- проверить новый слот;
- обновить запись;
- обновить событие Google Calendar.

## Защита от двойного бронирования

Это критическое требование.

Нельзя полагаться только на состояние Telegram-диалога.

Перед финальным созданием записи обязательно снова проверять слот.

На уровне БД использовать транзакцию.

### Решение: exclusion constraint обязателен

Перепроверка слота перед вставкой — не гарантия. Два запроса могут пройти проверку одновременно
и оба записать. Единственная настоящая защита — ограничение уровня БД:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE "Appointment"
  ADD CONSTRAINT appointment_no_overlap
  EXCLUDE USING gist (tstzrange("startAt", "blockedUntil", '[)') WITH &&)
  WHERE (status IN ('PENDING', 'CONFIRMED'));
```

Prisma не умеет выражать exclusion constraint в schema.prisma — это ручная SQL-миграция,
и она обязательна, а не «по возможности».

Код должен ловить ошибку PostgreSQL `23P01` (`exclusion_violation`) и превращать её
в сообщение «время только что заняли», а не в 500. Это же покрывает двойное нажатие
кнопки подтверждения.

Если слот уже занят:

```text
К сожалению, это время только что заняли.

Выберите другое свободное время.
```

После этого показать актуальные слоты.

Вся бизнес-логика работает в timezone:

Конвертация в локальное время выполняется только на уровне бизнес-логики и интерфейса.

Не использовать системный timezone сервера как источник истины.

## Напоминания

Минимально реализовать:

- напоминание клиенту;
- напоминание массажисту.

Рекомендуемые настройки должны быть конфигурируемыми.

Например:

```text
24h before
2h before
```

Не зашивать интервалы напоминаний глубоко в код.

Напоминание не отправляется для отменённой записи.

### Решение: напоминания хранятся в БД, а не в памяти

`setTimeout` и таймеры в памяти умирают вместе с процессом, а критерий готовности №10 требует,
чтобы бот переживал перезапуск. Поэтому:

1. при создании записи в таблицу `Reminder` пишутся строки на каждый настроенный интервал;
2. cron раз в минуту выбирает строки с `fireAt <= now()` и `sentAt IS NULL`;
3. после успешной отправки проставляется `sentAt`;
4. при переносе записи будущие неотправленные напоминания пересчитываются;
5. при отмене — удаляются;
6. пропущенные из-за простоя напоминания отправляются при старте, если ещё актуальны
   (не позже `REMINDER_GRACE_MINUTES` от `fireAt`), иначе помечаются как просроченные.

## Основные сущности

### User


### Appointment

```text

userId

startAt

blockedUntil
status

googleSyncState

```

`serviceId` обязателен: из услуги берутся `durationMinutes` и `bufferMinutes`, без неё
нельзя посчитать `endAt` и `blockedUntil`. В MVP сеется одна услуга по умолчанию.

`googleSyncState` нужен, потому что Google API может упасть уже после того, как запись
создана в БД. Запись при этом остаётся валидной, а досинхронизацией занимается фоновая задача:

```text
PENDING   событие ещё не создано в календаре
SYNCED    googleEventId актуален
FAILED    последняя попытка не удалась, нужен повтор
```

Статусы:

```text
PENDING
CONFIRMED
CANCELLED
COMPLETED
NO_SHOW
```

## Правила записи

Эти значения конфигурируются, а не зашиваются в код:

```text
BOOKING_HORIZON_DAYS      = 30    на сколько дней вперёд видны слоты
MIN_LEAD_TIME_MINUTES     = 120   нельзя записаться «через 10 минут»
CANCEL_DEADLINE_HOURS     = 4     позже — только через массажиста
RESCHEDULE_DEADLINE_HOURS = 4     то же для переноса
MAX_ACTIVE_APPOINTMENTS   = 3     сколько активных записей может держать один клиент
```

Без этих правил бот ведёт себя странно: показывает слот, до которого пять минут,
позволяет отменить сеанс, когда клиента уже ждут, и даёт одному человеку забить неделю.

Если клиент упирается в дедлайн отмены, бот не отказывает молча, а предлагает
связаться с массажистом и показывает контакты.

Не складывать всю логику в один `bot.ts`.

Telegram handlers должны быть тонкими.

Основная логика должна находиться в сервисах.

### Состояние диалога

Сессии Telegraf по умолчанию живут в памяти и умирают при перезапуске: пользователь,
застрявший на «введите телефон», получит сломанный сценарий. Поэтому состояние сцен
хранится в БД (таблица `BotSession`), а не в памяти процесса.

### callback_data

Лимит Telegram — 64 байта. Дату, время, услугу и намерение нельзя складывать в строку
текстом. Формат — короткий и разбираемый, с обязательной валидацией через Zod при разборе:

```text
bk:d:2026-09-10          выбор даты
bk:t:2026-09-10T12:00    выбор времени
ap:c:<appointmentId>     отмена записи
```

Идентификатор записи всегда проверяется на принадлежность текущему пользователю —
callback_data приходит от клиента и доверять ей нельзя.

### Решение: сервисный аккаунт вместо refresh token

Пока OAuth-приложение находится в статусе Testing, refresh token протухает через 7 дней,
и бот тихо перестаёт синхронизироваться с календарём. Для личного календаря массажиста
надёжнее сервисный аккаунт:

1. создать сервисный аккаунт в Google Cloud и скачать JSON-ключ;
2. расшарить календарь массажиста на почту сервисного аккаунта с правом
   «Вносить изменения в мероприятия»;
3. `GOOGLE_CALENDAR_ID` — адрес календаря массажиста.

Ключ не истекает, OAuth-экран проходить не нужно.

Секреты никогда не коммитить.

Создать:

```text
.env.example
```

# Критерии готовности MVP

MVP считается готовым, если:

1. Новый клиент может открыть бота и записаться без участия массажиста.
2. Занятый слот невозможно забронировать повторно.
3. Запись появляется в Google Calendar.
4. Массажист получает уведомление.
5. Клиент видит свою запись.
6. Клиент может отменить запись.
7. После отмены слот снова становится доступным.
8. Клиент может перенести запись.
9. Массажист может посмотреть свой график через Telegram.
10. Бот корректно переживает перезапуск сервера.

# Правила работы coding agent

При разработке:

1. Сначала изучить существующий код проекта.
2. Не переписывать рабочие части без необходимости.
3. Делать небольшие логические изменения.
4. После каждого этапа запускать:
   - typecheck;
   - lint;
   - tests.
5. Не добавлять зависимости без необходимости.
6. Любую новую ENV-переменную добавлять в `.env.example`.
7. Все миграции БД сохранять в репозитории.
8. Не хардкодить Telegram IDs, timezone, Calendar ID и секреты.
9. Бизнес-логику держать отдельно от Telegram handlers.
10. Перед завершением задачи проверить сценарий вручную от `/start` до создания записи.

# Приоритет разработки

Если требования конфликтуют, приоритет такой:

```text
1. отсутствие двойного бронирования
2. корректность расписания
3. синхронизация Google Calendar
4. отмена и перенос
5. уведомления
6. удобство интерфейса
7. визуальная красота
```

Основная цель первой версии — не красивый бот, а надёжная система записи, которую можно показать реальному массажисту как рабочее демо.
